## B4.2 — `docs/DEVELOPMENT.md`: provisioning, running, and runtime gates

Add (or replace) these sections, written for someone who has never run this project:
1. **Provisioning a database** — the exact order, and WHY it is that order:
   create the database → create `_sqlx_migrations` (version BIGINT PRIMARY KEY, description TEXT, installed_on
   TIMESTAMPTZ DEFAULT now(), success BOOLEAN, checksum BYTEA, execution_time BIGINT) → load
   `migrations/001_schema.sql` → insert the bookmark row `(1,'schema',true,decode('<sha384 of the file>','hex'),0)` →
   boot, so the migrator applies everything after 001 itself. The reason: the migrator creates that table inside the
   transaction it then rolls back on `relation already exists`, so loading the schema first leaves nothing to
   bookmark; and the bookmark's checksum must be the file's real sha384, computed with `sha384sum`.
2. **A migration rule that is easy to get wrong**: `migrations/001_schema.sql` is FROZEN — it is checksum-bookmarked,
   so changing one byte makes every existing database refuse to boot. Schema changes are additive files (`002_...`),
   never edits to 001.
3. **Running the server for a runtime gate**: copy `config.toml` to a scratch directory, change `[server] port`,
   keep `require_email_verification = false`, set `[discovery] directory_enabled = true` if the gate touches
   `/api/directory*`, and boot `/workspace/target/debug/komun-server` from that directory (it reads `config.toml`
   from its cwd). Include the health URL.
4. **The gates themselves**: `cargo build --workspace --all-targets`, `cargo test --workspace`,
   `touch crates/server/src/main.rs; cargo clippy -p komun-server --no-deps --message-format short` (the `touch` is
   required: cargo caches lint output and a second run prints nothing, which reads as zero warnings), and
   `cargo clippy --release -- -D warnings`, which must stay passing. Frontend: `cd web && npm run check && npm run build
   && npx vitest run`.
