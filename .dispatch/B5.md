# CARD B5 — Decouple advertised registration from the signup policy

**Owner:** Agent B (opencode) · **Branch:** `feature/agent-b` · **Worktree:** `/home/computing/repo-agent-b` (container `agent-repo-agent-b`, cwd `/workspace`)

## The decision (made by the user, not by you or by me)
A3 made `api/directory.rs` gate peer registration on `config.registration.mode`, and the discovery config no
longer carries any registration flag — so today one setting does two jobs: **whether this server lets people
sign up**, and **whether it advertises itself / accepts peers as openly registerable**. The user has chosen to
separate them with a distinct `discovery.open_registration` boolean. Implement exactly that; do not invent a
different shape or rename the concept.

## Task

**B5.1 — the flag.** Add to `DiscoveryConfig` in `crates/server/src/config.rs` (your file since B3):
```rust
/// Whether this server advertises itself as openly registerable, and whether it accepts
/// peer registrations into its directory. Deliberately SEPARATE from `[registration] mode`,
/// which governs user signup only.
pub open_registration: Option<bool>,
```
plus one method that resolves it: an explicit value wins; when unset it falls back to
`config.registration.mode == "open"`, so every existing config keeps its current behaviour. Use that method
everywhere you need the value — never `registration.mode` directly.

**B5.2 — the gate.** `api/directory.rs`'s `registration_is_open` becomes the resolved flag. A server whose users
sign up by invite only must still be able to accept peer registrations when the operator says so — that is the
bug this card fixes.

**B5.3 — what is advertised.** `tasks/registration.rs` includes `open_registration` in the payload it POSTs to
`directory_url`; `api/node.rs` includes the resolved value in the node/discovery response. Widen
`RegisterRequest` in `api/directory.rs` to accept the field with `#[serde(default)]` so an older peer that does
not send it still registers.

**B5.4 — store what peers advertise.** Add a NEW migration `migrations/002_directory_open_registration.sql`
adding `open_registration BOOLEAN NOT NULL DEFAULT true` to `directory_entries`, and read/write it in
`register_server` and the entry queries.
**DO NOT EDIT `migrations/001_schema.sql`.** Its sha384 is bookmarked in `komun_a`'s `_sqlx_migrations` (the
schema was hand-loaded, verified by the orchestrator); changing one byte of that file makes every boot of
`komun_a` fail with a checksum mismatch. An additive 002 is the only safe shape, and if you touch 001 the
runtime gate below will fail for a reason that has nothing to do with your code.

**B5.5 — `config.example.toml` is YOURS (one writer).** B added only the `[discovery] open_registration`
comment, as instructed. The file is otherwise still the pre-merge template — it carries `[auth] jwt_secret`,
`[federation]`, `[relay]` and `[discovery] registration_mode`, none of which the merged config struct still has
(they are silently ignored, which is why the server still boots). **The full rewrite is B4's**, as B filed it. Add `open_registration` under `[discovery]` with a
comment stating that leaving it out means "follow `[registration] mode`". This is also the file B4 documents,
so keep the wording you will want in the docs.
