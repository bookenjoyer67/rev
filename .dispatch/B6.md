# CARD B6 — Put coordinates back on new posts (click-to-place on your own map)

**Owner:** Agent B (opencode) · **Branch:** `feature/agent-b` · **Worktree:** `/home/computing/repo-agent-b` (container `agent-repo-agent-b`, cwd `/workspace`)
**Depends on:** A6 (merged — the frontend is flattened and at 0 errors / 0 warnings). **This card is B7's blocker in spirit:** finish it before B4 so the docs describe the shipped frontend.

## The gap, exactly

A6 deleted the old piggpin `<iframe>` picker from `web/src/routes/aid/new/+page.svelte` because it keyed off
`community.map_community_id`, `community.map_secret_hex` and `nodeInfo.relay_url` — and
`grep -rn "relay_url\|map_community\|map_secret" crates/server/src` returns **nothing**, so no handler ever emitted
any of the three and the picker could never activate. Removing it removed dead code.

But nothing replaced it. `location_lat` / `location_lon` are still sent when a post is created, and nothing in the
UI sets them any more, so posts have no coordinates and never appear as pins on your `/map`. That is a real feature
gap, not a cosmetic one.

**Do not resurrect piggpin.** The replacement is click-to-place on the Leaflet component you already built
(`web/src/lib/components/LocationMap.svelte`, B2) — no iframe, no relay, no map-community credentials.

## Task

**B6.1 — teach `LocationMap.svelte` a pick mode.** Today it takes `lat`/`lon`/`markers` and emits nothing. Add an
opt-in mode where a click on the map sets the marker and reports the coordinates back to the parent (a callback prop
or bindable values — your choice, but say which and keep the existing read-only usage on `/map` working unchanged).
Clamp to valid latitude/longitude and ignore nonsense values.

**B6.2 — use it in `web/src/routes/aid/new/+page.svelte`.** Show the map with a marker, let the user click to place
it, display the chosen coordinates as text, and give a clear way to remove them (a post without coordinates must
still be creatable — the field is optional). Keep sending `location_lat` / `location_lon` through the existing flat
client call; if the client's `create` signature no longer carries them, that is a bug in the flatten and you must fix
it in this card and say so.

**B6.3 — degrade honestly without tiles.** This container has no egress, so OpenStreetMap tiles will not load for you
and they may not load for a user on a locked-down network either. The coordinate picking must work and be provable
independently of tile rendering: assert the values the component emits, never the tiles. If a click cannot be
simulated in the test environment, extract the coordinate conversion into a small pure function, test that, and say
plainly in your report that the DOM interaction itself was not exercised.

**Do not** add a geocode-lookup button in this card. `/api/geocode` proxies Nominatim, which this container cannot
reach, so that path is unverifiable here — if you think it is worth having, file it as a note for a later card
instead of shipping something you could not test.
