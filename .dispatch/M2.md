Decisions the plan leaves open — implement these, they are deliberate:
- **Offers only on market threads.** A thread whose post kind is neither `listing` nor `want` answers 400
  ("offers are for listings and wanted ads"), so aid conversations keep their plain propose/accept flow.
- **`decline` maps to `withdrawn`** on the thread; `accept` maps to `accepted`; both are recorded as offer
  rows first so the trail is complete.
- **Currency precedence**: the offer's own currency, else the post's currency, else `[market]
  default_currency`; if none of the three exists it is a 400 naming the missing currency.

Task:
1. **M2.1 `POST /api/conversations/{match_id}/offers`** — participant-only (a non-participant gets 403, and
   an unknown id 404). Body: `kind` (offer|counter|accept|decline), `amount_cents` (required for
   offer/counter/accept, must be >= 0; rejected for decline), `currency` (optional per the precedence rule),
   `note` (optional, trimmed, max 500 chars). Rows are **append-only**: never update or delete one.
2. **M2.2 `GET /api/conversations/{match_id}/offers`** — participant-only, ordered by created_at, returning
   kind, amount_cents, currency, note, actor_id and created_at, so the UI can render the negotiation and
   show what was agreed.
3. **M2.3 Accept is atomic and means something.** Accepting an offer must, in ONE transaction: append the
   accept row, set `matches.agreed_price_cents` and `matches.currency` from the accepted offer, and set
   `matches.status='accepted'`. An accept on an already-accepted or completed thread is a 409 naming the
   current status. Accepting your OWN offer is a 409 — the counterparty accepts.
4. **M2.4 Completing a deal.** `PATCH .../status` to `completed` is allowed only from `accepted` (409
   otherwise, naming the current status) and must, in one transaction, set `matches.resolved_at=now()` and,
   when the thread's post is a listing or want: `posts.sold_at=now()`, `posts.buyer_id=<the other
   participant>`, `posts.status='fulfilled'`. Withdraw stays allowed from proposed or accepted by either
   participant and sets `resolved_at`.
5. **M2.5 Tests** in `tests/market.rs`: an aid thread refuses offers (400); a full offer → counter → accept
   → complete walk with the DB asserting `agreed_price_cents`, `currency`, `resolved_at`, `posts.sold_at`,
   `posts.buyer_id`, `posts.status`; an illegal transition matrix (proposed→completed, completed→accepted)
   each 409 with the current status in the body; a self-accept 409; a non-participant 403; an append-only
   check that the offer list contains every step in order.
