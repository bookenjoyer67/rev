## Why

SPEC A5 removes federation/alliances while keeping the directory. The three B3 edits remove the advertised
community data from `/api/node` and node registration and drop the community-scoped directory search; the
six diffs above remove the now-dangling module mounts/declarations and the `[federation]` config.

`cargo build --workspace --all-targets` exits 101 on this branch because of the **pre-existing**
`komun-core` test-compile error (`missing field image_path` in `crates/core/src/tests.rs`), which SPEC §2.1
records and A1.2/A2 own. It is unrelated to B3 — `komun-server`'s own test target does compile. The
non-`--all-targets` workspace build is clean.

## Recon gaps (things the card's table did not capture)

1. **`api/node.rs` also depended on federation beyond the two named fields.** It read
   `config.federation.domain` to compute `domain`. Removing `FederationConfig` without touching this would
   break the build, so B3's `node.rs` edit now derives `domain` from `config.node.public_url` only.
2. **`relay_url` was NOT already removed.** The card says the orchestrator had removed it, but at HEAD
   `api/node.rs` still had `relay_url: Option<String>` and `config.relay.external_url`. The B3 gate expects
   `/api/node` to carry no `relay_url`, so B3 removed it (the `[relay]` config section itself still
   exists and is not part of this card).
3. **The card's clippy expectation "≤ 3" is wrong for this branch.** Only rows 10–11 vanish with the
   deletions; rows 1–9 are still present because A2a (`auth/mod.rs`, `config.rs` impls, `repl.rs`) and A3
   (`db/communities.rs`, `db/endorsements.rs`, `api/endorsements.rs`) have not merged. Observed: 11 before
   deletions, 9 after.
4. **Other community (not federation) references remain and are out of B3's scope:**
   `api/admin.rs:146,153` (`communities_count` in the admin directory listing),
   `tasks/health.rs:32,35` (binds `communities_count` from the directory response),
   `db/communities.rs:73` (`UPDATE directory_entries SET community_locations = ...`). These are A-owned
   files that A3 deletes/rewrites; B3 did not touch them, and none references alliance/federation, so the
   grep gate is unaffected.
